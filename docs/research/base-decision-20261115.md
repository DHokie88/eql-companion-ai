## Cost and safety in both directions

**Community features into Oracle:** Community's Bazaar is wired from log chat through its Rust fold, item-name knowledge, module snapshots, UI, saved watches and alerts. Oracle's `engine/crates/fold/src/checkpoint.rs` returns no checkpoint if any registered module cannot checkpoint; the inspected Community `BazaarModule` has no checkpoint implementation. Adding it unchanged risks disabling Oracle checkpointing. A useful first technical spike is a read-only, isolated parser/fold integration with explicit checkpoint/restore and fixtures, followed by its UI, watch and export workflows. Do not ship a tab that lacks its engine or silently changes user data. This is a hypothesis and engineering scope, not a measured estimate.

**Oracle features into Community:** Oracle has `src/main/spellLibrary/` (28 files), `src/main/oracle/` (12 files), its item-data adapter, custom Gear/Build and five-loadout workflow; those named source directories do not exist in the Community snapshot. Path counts describe transfer surface, not quality, completeness or effort. Migrating the workflows also needs preload and IPC bindings, workers, engine contracts, settings, profile identity, tests, release and packaging. Community's release builder names its own test app and update feed; Oracle's `electron-builder.yml` names `com.eqoracle.app`. Preserve Oracle identity and do not inherit a donor updater or network behavior accidentally.

**Profile hazard:** Oracle's `src/main/channel.ts` dev directory is `everquest-companion-dev`. Community's `src/main/channel.ts` also names `everquest-companion-dev` for dev. Oracle's `CURRENT_SCHEMA_VERSION` is 15; Community's is 14, and Community's migration code contains newer-store handling. This establishes a collision and version mismatch, not proof of data loss. A donor must run only with an independently verified isolated userData path; test copied, synthetic profiles and reversibility before any migration. The live profile is not a test fixture.
